# Pipeline Memory 模板

核心理念：**最终能跑通的 pipeline 是主角**，写成干净、可直接复现的步骤序列；
中间的试错、弯路、踩坑单独作为"经验"记录。两者严格分开——读者应该能只看
"最终 Pipeline"一节就把事情重新跑通，而不必趟一遍你踩过的坑。

文件命名：`YYYY-MM-DD_HHMM_<简短任务描述>.md`（描述用 kebab-case，如
`2026-07-25_1430_build-auth-pipeline.md`）。这是**探索快照**，不自动加载。

> 当 pipeline 成熟稳定后，把下方"✅ 最终可跑通的 Pipeline"一节提炼进
> `pipeline_memory/PIPELINE.md`（单一真相源、无弯路、无时间戳命名），
> 并由项目 `CLAUDE.md` 用 `@pipeline_memory/PIPELINE.md` 导入自动加载。
> 详见 SKILL.md 第 5 步。

```markdown
# <任务标题>

**日期时间**: YYYY-MM-DD HH:MM
**工作目录**: <cwd>
**Git 分支/commit**: <branch @ short-sha，非 git 仓库则写 N/A>
**状态**: 已跑通 / 部分跑通 / 未跑通
**标签**: #tag1 #tag2

## 会话概览
用 2-4 句话概括目标是什么、最终是否跑通、产出在哪。
让未来的读者读完这段就能接上下文。

## ✅ 最终可跑通的 Pipeline（主角）
这是最重要的一节。写成**干净、有序、可直接复现**的步骤，剔除所有试错过程。
读者照着这些步骤就应该能重新得到成功结果。

前置条件 / 环境假设：
- <依赖、版本、环境变量键名、需要的凭证（用键名，不写明文）>

步骤：
```bash
# 步骤 1：<做什么>
<命令>

# 步骤 2：<做什么>
<命令>
```

关键配置 / 代码改动：
- `<文件路径>`: <改了什么，为什么这样是对的>

验证方式（如何确认跑通）：
```bash
<验证命令>
```
预期结果：<成功时应看到什么>

## 💡 弯路与经验（配角）
记录到达上面那条干净路径之前，试过但没走通的方案、踩过的坑。
这部分是"为什么最终方案长这样"的注脚，帮未来避免重走弯路。

- **试过**: <做了什么> — **结果**: <为什么没走通/报什么错> — **教训**: <由此得到的结论，如何指向最终方案>
- **坑**: <非显而易见的陷阱/错误信息> — **根因**: <根本原因> — **规避**: <如何避免>

## 关键决策
仅记录影响最终 pipeline 形态的重要选择（代码本身看不出的"为什么"）。

- **决策**: <选了什么> — **原因**: <为什么> — **放弃**: <放弃了什么方案及原因>

## 产出与指标
- **产出物**: <生成的文件/构建产物/报告，附路径>
- **指标**: <耗时、通过率、性能数字等，如有>

## 下一步 / 未解决
- <若状态非"已跑通"，明确写还差什么、下一步该做什么，方便续接>

## 相关资源
- <相关文件路径、文档链接、ticket>
```

## 填写要点

- **主配分明**：最终 Pipeline 一节只放走得通的干净步骤，任何试错都归入"弯路与经验"。
  不要把失败的命令混进最终 pipeline。
- **可复现**：最终 pipeline 的命令和路径要具体、有序，让别人能照着一次跑通。
- **诚实**：状态如实标（已跑通/部分跑通/未跑通）；验证失败就写失败并贴输出。
- **弯路要有结论**：每条弯路都要落到"教训"或"由此选择了 X"，否则只是流水账。
- **不泄密**：密钥/token/`.env` 用键名引用（`API_KEY=<redacted>`），绝不写明文值。
- **精炼**：弯路只记非显而易见、对未来有价值的，琐碎试错不必记。
