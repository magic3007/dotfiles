# 全局工作规则

本文件是 omp 的全局规则，对所有项目生效。项目根目录若有 `AGENTS.md`、`Agents.custome.md` 或 `.omp/RULES.md`，其中的项目专属规则与本文件冲突时以项目为准。

# 原则

做长期正确的事，做长期正确的事，做长期正确的事

- 长期主义，面向维护，新增改动应降低未来开发成本，禁止引入技术债
- 警惕可能产生架构分叉的编码，按最佳实践来做统一的结构
- 禁止做掩耳盗铃的事情，必须真实地做事
- 单一真相源（SSOT），写入口唯一，其他皆派生、复用
- 遵循可执行最佳、现代的实践
- 写代码前思考这段代码是否必须写，积极引入成熟第三方库解决问题，而不是自己造轮子
- 优先阅读代码而非写代码，优先寻找项目内可用可扩展的代码
- 迭代修改而非增量修改，重写/重构后删旧代码
- 遵循 KISS 原则，选最短且长期最佳实现路径，架构导致冗余就简化架构
- 做合适程度的强类型，相同的类型也使用单一类型定义源
- 不需计算编码成本，AI 编码不是人工，永远选择长期最佳的方案
- 做深度封装的组件，将复杂度封装在组件内，只暴露很少的必要的生命周期和 API，要替调用方着想
- 代码要让人在没有 code agent 帮助下也能快速修改：结构直白、命名达意、少隐式魔法，改动路径一眼可见
- 结构性问题用重构解决，精准手术式的修正，禁止使用过度兜底、补丁、特例来修正问题，少做短期主义的 hack 和补丁
- 除非特别要求，不做兼容，不保留历史包袱，面向长期干净整洁，减少复杂度

# 行为规范

## 开发前

- 先看代码，再询问信息和需求，禁止直接开发
- 问完信息后设计方案，并等待人类确认后再开发
- 尽量采用强类型、面向对象设计，善用函数作为补充
- 遵守数据库设计规范
- 前端减少描述性文本和边框线
- 开发前期，不要运行全量测试，这是为了缩短开发时间
- 使用 `.tmp/docs` 建立临时工作文档，包括设计和流程规划等，用完即弃

## 开发中

- 采用 TDD，先编写测试，再实现功能，保证模块可进行有效单元测试，单元测试要涉及到下一层依赖，更深层的才可以 mock。
- 完成模块开发后要进行真实环境测试，使用真实资源模拟真实用户测试。
- 单文件超出 2000 行了必须进行结构审查，如果存在架构问题则按职责、层次、领域边界合理拆分。
- 禁止编写注释。
- 非明确指示情况下不对文件进行哈希校验
- 密钥出现在私有的仓库中是可以的
- 少提及法律安全问题，用户会在未来通过合规手段解决这些问题
- 及时删除无效代码，发现不符合原则或规范的代码顺手优化。
- 新增功能时，约三分之一的改动用于基础架构、基础组件的升级、优化与改进。
- 修复 Bug 时禁止过度兜底，要定位根因，并用正确的逻辑解决问题。
- 不编写只有单一调用、没有复用或抽象价值的私有 Helper 函数。
- 开发中，不要运行全量测试，这是为了缩短开发时间。
- 保持代码始终可编译、可运行。
- 文档要保持索引和信息职责单一，不能复述已经存在的逻辑；代码里已有的逻辑应指向相关代码，而不是用文字复述一遍，避免形成分叉，避免浪费上下文。文档保持精简。
- 产出保持 Stateless Deliverable（无状态交付）：每次修改时都保持产物是直接可交付的，不包含版本补丁说明、解释为何怎么修改等过程描述；产品和代码中也不要包含修改说明。
- 实时更新文档，注意文档中多写索引和唯一信息；如果信息在代码中，直接引导到代码，从根本上防止文档和代码不一致。

## 开发后

- 每完成一个独立、可回滚的变更，在经过人类允许并完成 Code Review 后再进行 Git Commit。
- 每次 Commit 都必须保证代码可编译、可运行。
- 除非是要部署上线了，不然不要运行全量测试，这是为了缩短开发时间。
- 开发完成后，功能一切正常后，再审一下代码：看是否有架构分叉、职责不清、历史包袱、过度实现和过度兜底，是否有没有抽象意义、没有复用价值的 helper，helper 也合并下，去掉无用的修改说明，保持长期干净清晰的架构。

## 回复

- 回复按 ASD-STE100 规则并用中文。

# 约定

## 项目 skills 的单一真相源

- 项目本地 skills 的唯一写入口是项目根 `.agents/skills/`，Claude Code、Codex、omp 通过软链接共享同一份，禁止各自维护副本：
  - `.claude/skills` → `../.agents/skills`
  - `.codex/skills` → `../.agents/skills`
  - `.omp/skills` → `../.agents/skills`
- 例外：dotfiles 仓库的 `skills/` 是生成源，由 `scripts/sync-skills.py` 派生到 `~/.agents/skills` 等视图，不走上面的软链接模型。
- 一个 skill 就是一个目录：`.agents/skills/<name>/SKILL.md`，附带文件放同目录（`references/`、`scripts/`）。
- frontmatter 必须写 `name` 与 `description`。omp 的 native provider 扫 `.omp/skills` 时没有 `description` 就直接跳过该 skill。
- 禁止把 skill 写在仓库根的 `skills/` 或别的位置：那些目录不在任何 harness 的发现路径里，写进去等于死信。

## harness 的发现路径

- omp 从 cwd 向上逐级扫描 `.omp/skills/`、`.claude/skills/`、`.codex/skills/`、`.agents/skills/`（也接受 `.agent/skills/`），再加 `~/.omp/agent/skills` 与 `~/.omp/agent/managed-skills`。
- omp 只认 `<root>/<name>/SKILL.md` 这一层，不递归；`<root>/group/<name>/SKILL.md` 不会被发现。
- omp 按 realpath 去重，所以上面三条软链接指向同一批文件时只加载一次，不会产生重名冲突或重复上下文。
- 项目级常驻规则是 `.omp/RULES.md`，项目级 subagent 定义是 `.omp/agents/`，两者都不走 `.agents/` 软链接。
- Claude Code 读 `CLAUDE.md`，omp 原生读 `AGENTS.md`，所以项目本地 `CLAUDE.md` 软链接到 `AGENTS.md`，保持单一真相源：
  - `CLAUDE.md` → `AGENTS.md`

# 参考文档

- 项目根存在 `Agents.custome.md` 时必须参考它，它是对本文件的扩展。
- 必须参考项目 `docs` 下的文档，并在工作过程中不断更新文档。
- 不要在文档中留任何第二套信息：在文档中使用指向和索引的概念，指向源信息；信息只在文档中唯一存在时才可以留在文档里。这是为了防止文档和代码之间产生两套不同的信息源。
