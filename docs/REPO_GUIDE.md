# REPO_GUIDE

This is the one place that states how the repository works. `README.md` sells it
to a visitor, `AGENTS.md` points agents here, and `.repo-std/` enforces what can
be enforced. Nothing below is repeated elsewhere; where a fact lives in code,
this document points at the file instead of restating it.

Audience: someone with no coding agent who has to change one thing and be sure
it took effect.

## 1. What this repository does

It stores configuration and installs it with
[Dotbot](https://github.com/anishathalye/dotbot), in two phases:

| Phase | Content | Network |
|---|---|---|
| 1 | directories, submodules, backups, symlinks, config merges, skill views | never needed |
| 2 | Homebrew/apt packages, oh-my-zsh, node, the AI harnesses, Herdr | needed, every step is timeout-guarded and `|| true` |

`./install` runs both and is idempotent. `sync.sh` runs a cut-down phase 1 every
15 minutes from `sync.conf.yaml`.

There is **no dry-run flag**. The pinned Dotbot submodule rejects `-n` and
`--dry-run`. To preview, run the single directive you care about:
`./install --only link` is idempotent and refuses to overwrite a regular file.

## 2. The three ways a config reaches the machine

This is the decision every new config faces. Getting it wrong corrupts the
repository, so it is also the first thing `.repo-std/gate.sh` checks.

| Does the owning tool rewrite the file itself? | Delivery | Where you add it |
|---|---|---|
| No | **link** | both `install.conf.yaml` and `sync.conf.yaml` |
| Yes, and repo keys must win over local state | **merge** | a `scripts/*-config-sync.py`, called from `scripts/post-install.d/` and from the `shell:` section of `sync.conf.yaml` |
| Yes, and only the initial content matters | **seed** | `scripts/post-install.d/10-seed-configs.sh` |

Why "rewrites itself" decides it: those tools save by writing a temp file and
renaming it over the config path, without resolving the realpath. The rename
replaces the symlink with a regular file. Machine-local state then sits in the
repository, and the next Dotbot run aborts the **whole link section** with
"already exists but is a regular file or directory" — not just that one entry.

Currently merged: Codex (`codex/config.toml`), mcode (`mcode/config.yaml`),
Antigravity CLI (`antigravity/cli-settings.json`). Currently seeded: kimi
(`kimi-code/config.toml`), the Herdr app's `settings.json` and `keys.json`.
Enforced by `.repo-std/checks/no_link_for_self_rewriting_configs.py`.

Consequence of merging: a setting toggled in that tool's UI is reverted at the
next sync. Change the tracked file instead.

## 3. Single source of truth

| Fact | Lives in | Everything else |
|---|---|---|
| which symlinks exist | `install.conf.yaml` + `sync.conf.yaml` | kept identical by `.repo-std/checks/link_parity.py`; asymmetries declared in `.repo-std/link-exemptions.yml` |
| shared skills | `skills/` | the per-harness views under `~/` are generated by `scripts/sync-skills.py`; never edit a view |
| harness-only skills | `claude/skills/`, `codex/skills/`, `pi/skills/`, `omp/skills/` | a skill is shared unless it depends on one harness |
| omp plugins | `omp/plugins.txt` | `~/.omp/plugins` is runtime state; `scripts/omp-plugins.sh` installs the missing ones |
| shell aliases and functions | `common_shell_setup.sh` | sourced by both `.bashrc` and `.zshrc` |
| credentials | `~/.common_shell_setup_local.sh` (untracked) | tracked files hold a *reference*: an env-var name, `${VAR}`, or `!command` |
| rules and process | this file | `AGENTS.md` and the local skill are pointers |
| lessons and their enforcement | `.repo-std/corrections.yml` | each entry names a check that fails |

Machine-specific overrides are the `*_local` files listed in `README.md`; they
are gitignored by design.

### 3.1 Skills: one source, generated views

Each harness looks for skills somewhere different, so the repository keeps one
source per skill and generates every view with `python3 scripts/sync-skills.py`
(run by `./install` and by every sync tick).

| Source | Scope | Generated view | Read by |
|---|---|---|---|
| `skills/` | shared | `~/.agents/skills/<name>` | Codex, Pi, omp, mcode, Cursor natively |
| `claude/skills/` | Claude Code only | `~/.claude/skills/<name>` | Claude Code — the view also gets every shared and external skill, because Claude Code ignores `~/.agents/skills` |
| `codex/skills/` | Codex only | `~/.codex/skills/<name>` | Codex |
| `pi/skills/` | Pi only | `~/.pi/agent/skills/<name>` | Pi |
| `omp/skills/` | omp only | `~/.omp/agent/skills/<name>` | omp |
| — | shared + external | `~/.gemini/config/skills/<name>` | Antigravity CLI, which reads global skills only there |

A skill is **shared** unless it depends on one harness: Claude-only runtime
features (backtick-command injection, `${CLAUDE_SKILL_DIR}`, plugin hooks), or
configuring/operating that harness, or generating that harness's project files.
A shared skill references its own files through `~/.agents/skills/<name>/…`,
which exists for every harness.

Three properties of the views that are easy to break:

- A view is a **real directory of per-skill symlinks**. Never symlink a whole
  view back into the repository: harnesses that recurse would list the same
  skill twice, and a tool writing into the view would write into the repository.
- A bundle (several skills under one directory) is flattened to one entry per
  frontmatter `name`, which is why `skills/canvo` is exported as `canvo-op`.
  Directory name and frontmatter name may legitimately differ.
- Third-party installs (`npx skills add <pkg> -g`) land in `~/.agents/skills`
  and are tracked in `~/.agents/.skill-lock.json`, outside this repository.
  Re-run the sync afterwards so Claude Code and the Antigravity CLI see them.

This repository is public. An internal skill stays out of it by being listed in
`.gitignore`; `.repo-std/checks/private_skills_ignored.py` fails when an
untracked skill directory is not.


## 4. Change paths

Each row is a whole task: where to start, what to touch, how to know it worked.

| I want to… | Start at | Then | Verify |
|---|---|---|---|
| add a config file | the table in §2 | add the entry to **both** dotbot configs, or write the merge/seed step | `bash .repo-std/gate.sh` then `./install --only link` |
| add a shell alias | `common_shell_setup.sh` | one function or alias, next to its siblings | `bash -n common_shell_setup.sh`, then open a new shell |
| add a skill | `skills/<name>/SKILL.md` | frontmatter needs `name` and `description`; put a harness-specific one under that harness's directory | `python3 scripts/sync-skills.py --dry-run` |
| keep a skill private | `.gitignore` | add the directory path; this repository is public | `bash .repo-std/gate.sh` |
| change an omp model or role | `omp/models.yml`, `omp/config.yml` | `config.yml` takes **no comments** — explanations go in `omp/README.md` | `omp models`, then start a session |
| change a Codex/mcode/Antigravity setting | the tracked file named in §2 | never the live file under `~/` | re-run the matching `scripts/*-sync.py` |
| make a GUI app start at login | `grok-bot/README.md` | XDG autostart entry linked from **both** dotbot configs, `if:`-guarded on the absolute launcher path | `bash .repo-std/gate.sh`, then log in again |
| record a correction | `.repo-std/` | §5 | `bash .repo-std/gate.sh --prove` |

Harness-specific depth that does not fit a table: `omp/README.md` (models,
gateways, plugins), `herdr/README.md` (plugins), `herdr-app/README.md`,
`neovim/README.md`, `archive/fish/README.md` (frozen).

## 5. Corrections become checks

A correction written into a document protects nothing: the next person must read
the right paragraph at the right moment. A correction written as a check fails
loudly, forever, including for the version of this repository that has forgotten
why.

So: **a lesson is not recorded until a check fails on it.**

1. Write the check as `.repo-std/checks/<name>.py`. It takes `--root`, prints one
   line per violation, exits non-zero when there is any.
2. Write a violating sample under `.repo-std/checks/fixtures/<name>/` — a minimal
   tree the check must reject. When real git state is needed, write an executable
   `prove.sh` there instead, exiting 0 when it observed the failure.
3. Register it in `.repo-std/corrections.yml` with the `origin` (what went wrong,
   when) and the `rule` (one judgeable sentence).
4. `bash .repo-std/gate.sh --prove` must show your check rejecting its fixture.

`.repo-std/checks/corrections_ledger.py` is the guard over the guards: it fails
when a check has no ledger entry, when an entry names a check that no longer
exists, or when a check has no fixture. That is what keeps the ledger from
decaying back into prose.

A lesson no repository state can assert (a platform behaviour, a runtime race)
stays prose — and must say *why* no check is possible. Current example: a
machine-local `~/.zshrc_local` that is a copy of the main zshrc sends zsh
startup into infinite recursion; the file is untracked, so nothing here can see
it. The defence is that `oh-my-zsh/zshrc` sources `~/.zshrc_local` last and
expects overrides only.

## 6. Verification

```bash
bash .repo-std/gate.sh            # every check, against the repository
bash .repo-std/gate.sh --prove    # every check, against its violating fixture
python3 scripts/sync-skills.py --dry-run
./install --only link             # idempotent; relinks without touching phase 2
```

CI (`.github/workflows/gate.yml`) runs the first two and nothing else, so a check
added locally is in CI in the same commit.

## 7. Boundaries

- **Vendored trees** — `skills/scientific-agent-skills/`, `dotbot/`, `vim/vimrc/`,
  `neovim/`, `oh-my-zsh/` plugins. Upstream owns their contents; the checks skip
  them and only the integration edges are our business.
- **Archived** — `archive/fish/`. Frozen so an existing fish login keeps working.
  Do not add to it.
- **Runtime state** — anything under `~/` that a tool writes: sessions, caches,
  lockfiles, `~/.omp/plugins`, `~/.minimax/` except `config.yaml`. It never comes
  back into the repository.
- **Standalone tools** — `scripts/backup_to_NAS.sh`, `scripts/mount_sshfs.sh`,
  `scripts/tailscale-setup.sh`, `scripts/yolo-generic.sh`. Run by hand or by one
  install step; they are not part of the link/merge/seed model.
