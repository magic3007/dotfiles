# 过时裁决与单一真相源

## 判过时：三问

对盘点报告里的每个候选依次回答，三问都通过才允许删除。

1. **谁在引用它？** 用仓库内全文搜索确认（文件名、模块名、符号名、配置键）。零引用是必要条件，不是充分条件：入口文件、CI 调用、运行时按字符串加载的插件都会表现为零引用。
2. **它和现行实现是否矛盾？** 描述的行为与代码不符的文档、与当前接口不符的示例、与现行流程不符的脚本，都是负资产，矛盾本身就是删除理由。
3. **删掉谁会发现？** 答不出就不是"安全删除"，而是"未知"。未知走下面的隔离流程，不走删除。

## 删除的执行方式

- 删除独立成提交，不与功能改动混在一起；提交信息写清"为什么它过时"（谁取代了它）。
- 先删引用，再删被引用者，每步保持基线命令全绿。
- 不留墓碑：不保留注释掉的旧实现、不保留 `_old` / `_v1` / `deprecated_` 副本、不保留"为了兼容"的转发函数。需要回头看的内容在 git 历史里。

## 不确定时：隔离而不是沉默保留

无法回答第三问时，把不确定本身变成记录，而不是让文件静静留着：

1. 在 `.repo-std/corrections.yml` 登记一条 `waived` 条目，`rule` 写"确认 `path/to/thing` 是否仍在使用"，`waiver.surfaced_in` 写它会在哪里被重新看到，`revisit` 填一个具体日期。
2. 可行时加一条廉价的运行期证据：对疑似死代码加一行日志或计数，下个周期回来看有没有被打到。
3. 复查日期到了 `corrections.py verify` 会失败，强迫重新裁决。沉默保留不会，所以不要沉默保留。

## 多来源冲突：确定唯一真相源

同一事实出现在多处（README、docs/、AGENTS.md、代码注释、wiki 导出）时，按顺序裁定：

1. **可执行者优先**：代码、检查脚本、CI 配置描述的事实，永远压过文字描述。文字与之冲突的部分直接删，不"更新成一致"——一致只能维持到下次改代码。
2. **被依赖者优先**：被其他文档引用最多、被 CI 或入口引用的那份，留作真相源。
3. **与行为一致者优先**：前两条打平时，实测哪份与当前行为一致，留哪份。
4. **维护者裁决**：仍然打平时问人，并把裁决理由写进真相源文件，避免下次重演。

裁定后的动作固定为三步：把唯一正文留在真相源 → 其余位置改成一句话指针（含路径）→ 指针无价值的直接删。

## 不要复述

规范文档里出现下面这些写法时，说明正在制造第二份真相源，改成指针：

- 抄接口签名、字段列表、默认值、目录树 → 指向定义处。
- 抄命令的全部参数 → 指向 `--help` 或 Makefile 目标。
- 抄检查规则的细节 → 指向 `.repo-std/checks/` 下的脚本。

规范文档只该独占这些内容：为什么这么设计、做过哪些取舍、从哪里开始改、怎么验证。这些在代码里确实不存在。

## 生成物与 vendored

- 生成物（构建产物、锁文件、自动生成的客户端代码）不参与"重复"裁决；它们的真相源是生成器。做法是加一条检查：重新生成后 `git diff --exit-code` 必须干净。
- vendored 的第三方源码不整改内部，只管边界：记录来源与版本、禁止就地修改（改了就打补丁文件），并用检查守住"不得直接编辑 vendor 目录"。
