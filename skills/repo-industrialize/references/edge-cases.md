# 边界情况

## 判不准是否过时

症状：零引用，但可能被运行时按字符串加载、被外部仓库引用、被某个人手动跑。

做法：不删，但也不沉默保留。按 [ssot.md](ssot.md) 的隔离流程登记一条 `waived` 纠正（规则写"确认 X 是否仍在使用"，填 `revisit` 日期），可行时加一行运行期计数作为证据。复查日期到了 `corrections.py verify` 会失败，强制重新裁决。

反模式：加一句"疑似废弃"的注释然后留在原地——它不会提醒任何人。

## 纠正无法自动化

按 [correction-to-check.md](correction-to-check.md) 的降级阶梯逐级往下，不要一步跳到"写进文档"。尤其注意第 2 级：近似检查宁可漏（假阴）也不可误（假阳）。假阳会逼人加豁免，豁免一多规则就名存实亡。

真的只能人工时，`waived` 条目的 `surfaced_in` 必须是一个人**必定会看到**的位置：PR 模板必填项、CODEOWNERS 强制评审、CI 的显式 warning。写成"团队规范文档第 3 节"等于没写。

## 仓库过大或结构混乱

不要一次性整改整个仓库——大改动评审不动，也回滚不了。分片：

1. 先只做全仓库级、低风险的一类事：删除确定的过时内容，或接上 CI 闸门（哪怕初始阈值就是"不得变差"）。闸门先行可以防止一边整理一边回潮。
2. 按**所有权或构建单元**切片（不是按文件数平均切）。每片独立走阶段 1–3，各自保持绿。
3. 先在一片上跑完整流程并产出 `docs/REPO_GUIDE.md` 的骨架，验证流程有效，再推广到其他片。
4. 结构混乱到无法判断边界时，先用 `inventory.py --json` 的依赖线索（同名文件、重复内容、无人引用）画出事实上的簇，按簇切。

阶段 5 的纠正台账是全仓库级的，不随分片切开——它是整个仓库的闸门。

## 多来源文档互相矛盾

按 [ssot.md](ssot.md) 的仲裁顺序定唯一真相源。两点容易做错：

- 不要"把两份都更新成一致"。两份一致只能维持到下一次改动，仍然是两个真相源。
- 不要把外部 wiki 的内容抄进仓库。要么把它迁进仓库并在 wiki 留指针，要么反过来；两边都留正文一定会漂。

## 生成物与 vendored 目录

生成物（构建产物、自动生成的客户端、锁文件）不参与重复裁决，真相源是生成器。加一条检查：重新生成后 `git diff --exit-code` 干净。

vendored 第三方代码不整改内部。只守边界：记录来源与版本、禁止就地编辑（要改就维护补丁文件）、把 vendor 目录排除在质量检查范围之外，否则检查会被第三方代码的噪声淹没。

## 仓库不干净或有人并行改

阶段 0 要求工作区干净。有未提交改动时先确认归属：是自己的就先提交或 stash；是别人/其他会话的，就只在自己负责的路径上作业，按路径分区提交，提交前核对暂存树只含自己的改动。

## 基线本来就是红的

不要把"让测试变绿"和"整理仓库"混在一起做。先记录红的清单与原因，在阶段 3 里作为独立提交修复；修不了的标记为已知失败并登记进台账（带复查日期），让它不再被当成噪声忽略。

## 没有 CI

没有流水线时，检查仍然要写，入口固定为一条本地命令（`make check` 或 `.repo-std/gate.sh`），并挂到 pre-push git hook。能跑的检查在本地也有价值；缺的只是强制性，这个缺口要写进 `docs/REPO_GUIDE.md` 的已知缺口节，而不是默默跳过。
