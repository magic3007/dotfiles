# 工业级质量标准与可改性

两份清单。上半部分管"不出事"，下半部分管"别人能改"。逐条对照，不逐条照抄进目标仓库的文档——目标仓库只记录与它自身有关的偏离与取舍。

## 一、工业级清单

### 失败路径

- 每个外部调用（网络、文件、子进程、数据库）都要明确：失败时抛还是返回、重试几次、超时多少。没有超时的网络调用按缺陷处理。
- 不吞异常。`except: pass` 和空 catch 要么补上处理，要么让它抛。
- 错误信息带上定位所需的事实（哪个路径、哪个 id、期望什么实得什么），不带敏感值。
- 不为掩盖未知状态而兜底。兜底写法掩盖根因，使下一次故障更难查——先定位，再决定是否需要兜底。

### 边界与输入

- 外部输入在进入核心逻辑前校验，并且只校验一次（入口校验，内部信任）。
- 空集合、单元素、超大输入、并发重入，这四种情况在测试里至少覆盖会出事的那几个。

### 结构

- 一个模块一个职责；文件超过约两千行必须做职责审查并拆分。
- 依赖方向单向：上层依赖下层，禁止反向与环。能用检查守住就写检查。
- 不写只有一个调用点、也没有抽象价值的私有 helper——直接内联，减少跳转。
- 重构即替换：新实现落地后删旧实现，不保留开关、别名、转发层。

### 类型与命名

- 同一概念一个类型定义源，不同层各写一份结构体是分叉的开始。
- 命名说清楚是什么，不说怎么实现；布尔值用肯定式（`enabled` 而非 `not_disabled`）。
- 缩写只用领域内公认的；同一概念全仓库一个词，不要 `user`/`account`/`member` 混用。

### 依赖

- 版本锁定且可复现；锁文件进版本库。
- 新增依赖前先找仓库内已有实现，再找标准库，最后才引入第三方；引入时记录为什么选它。
- 删除代码时同步删除它带来的依赖。

### 测试

- 覆盖"会出事的分支"优先于覆盖率数字：失败路径、边界、曾经出过的 bug。
- 单元测试触达下一层真实依赖，再深的才 mock；全 mock 的测试只验证了 mock。
- 测试必须确定性、可并行、与执行顺序无关；禁止依赖真实时钟与真实网络。
- 不写同义反复的测试（断言常量、断言不抛、断言长度变大）。

## 二、可改性清单（面向没有 agent 的人）

判据：一个没读过这个仓库的人，接到典型任务后，能不能在十分钟内找到改动点并验证？

- **入口可发现**：从仓库根出发，一眼能看出程序从哪开始跑。做不到就改目录与命名，而不是写更长的 README。
- **路径短**：典型改动落在一到两个文件内。改一个行为要动五处，说明职责被打散了，这是结构问题。
- **少隐式魔法**：动态注册、字符串反射加载、按文件名约定自动发现、深层继承，这些都让人找不到调用关系。保留时必须在 `docs/REPO_GUIDE.md` 写明"从哪里能列出全部实例"。
- **配置集中**：配置项有唯一定义处，默认值和读取处在一起，不散落在多个模块。
- **验证命令可复制**：改完怎么验证，是一条能直接粘进终端的命令，不是一段叙述。
- **失败信息自解释**：常见错误的提示里直接写下一步该做什么。
- **注释策略**：本仓库不写解释代码在做什么的注释——读代码就知道。需要解释的是"为什么"，而"为什么"属于 `docs/REPO_GUIDE.md` 的决策记录，不属于代码行间。名字取不好才需要注释，先改名字。

## 三、整改顺序

先结构，后风格。顺序错了会反复返工：

1. 删除（过时内容）——减少后面所有工作的面积。
2. 修结构（职责、依赖方向、重复实现）。
3. 补失败路径与测试。
4. 统一命名与类型源。
5. 风格与格式（交给 formatter，不手工做）。

每一类改动独立成提交，保持每个提交可编译、可运行。
