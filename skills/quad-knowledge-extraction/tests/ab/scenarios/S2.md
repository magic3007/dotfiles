# 会话记录 S2：docker compose 起来后首个请求 ECONNREFUSED 127.0.0.1:5432

## 环境

```
$ docker --version
Docker version 27.3.1
$ docker compose version
Docker Compose version v2.29.7
```

`docker-compose.yml`（节选）：

```yaml
services:
  db:
    image: postgres:16.4
    environment:
      POSTGRES_PASSWORD: dev
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 2s
      timeout: 3s
      retries: 30
  api:
    build: .
    environment:
      DATABASE_URL: postgres://postgres:dev@db:5432/app
    depends_on:
      - db
    ports: ["3000:3000"]
```

## 现象

`docker compose up` 之后立刻 `curl localhost:3000/healthz`，约 40% 概率报：

```
api  | Error: connect ECONNREFUSED 127.0.0.1:5432
api  |     at TCPConnectWrap.afterConnect [as oncomplete] (node:net:1637:16)
```

注意报错里的地址是 `127.0.0.1:5432`，**不是** `db:5432`。等 5~10 秒再请求就好了。
`docker compose logs db` 里能看到 `database system is ready to accept connections` 出现过两次
（一次是初始化期的临时实例，一次是真正启动）。

## 调查过程

尝试 1（失败）：在 `api` 里加连接重试（`pg` 的 `connectionTimeoutMillis` + 指数退避 5 次）。
本地连续 20 次 `up` 有 3 次仍然失败。缓解但没根治。

尝试 2（失败）：怀疑是 db 容器没起来，`docker compose ps` 显示 `db` 一直 `healthy`，
`api` 状态 `running`。排除容器未启动。

关键观测：

```
$ docker compose exec api printenv DATABASE_URL
postgres://postgres:dev@db:5432/app
$ docker compose exec api node -e "require('dns').lookup('db',(e,a)=>console.log(e,a))"
null '172.20.0.2'
```

容器内 DNS 解析正常，`DATABASE_URL` 也确实是 `db`。

```
$ docker compose exec api node -e "require('net').connect(5432,'db').on('error',e=>console.log('ERR',e.code)).on('connect',()=>console.log('OK'))"
ERR ECONNREFUSED
```

直连 `db:5432` 在容器内也 refused → 说明此刻 Postgres 还没监听。

```
$ docker compose config | grep -A4 depends_on
    depends_on:
      db:
        condition: service_started
```

`depends_on` 的裸列表写法等价于 `condition: service_started`，即"容器进程启动了"，
**不是**"healthcheck 通过了"。虽然 db 定义了 healthcheck，但没人引用它。

至于报错里的 `127.0.0.1`：`pg` 驱动在拿到 `db` 的 A 记录失败后，日志里打印的是 socket 的
本地端点，看起来像 localhost，容易误导——这一点是我从 `pg` 源码读出来的（`packages/pg/lib/connection.js`
里 `Error: connect ECONNREFUSED <localAddress>:<localPort>` 走的是系统 errno 文案），
**我没有实测**把 errno 文案与远端地址对应起来，属于推断。

## 最终修复（已验证）

```yaml
  api:
    depends_on:
      db:
        condition: service_healthy
```

验证：

```
$ for i in $(seq 30); do docker compose down -v >/dev/null 2>&1; docker compose up -d >/dev/null 2>&1; sleep 1; curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/healthz; done | sort | uniq -c
     30 200
```

30 轮全部 200，`docker compose logs api | grep -c ECONNREFUSED` 输出 0。

## 顺带发现（未验证）

- 没验证 Kubernetes（readinessProbe + initContainer）下等价做法。
- 没验证 `restart: unless-stopped` 是否也能掩盖这个问题。
- healthcheck 的 `retries: 30` × `interval: 2s` 意味着最长 60 秒才判 unhealthy，
  我没测过把 retries 调小对启动时长的影响。

## 另一个看起来一样的报错（不同根因，供对照）

同一套 compose 在另一台机器上报 `ECONNREFUSED 127.0.0.1:5432`，但**每次都失败、等多久都不行**。
那次根因是 postgres 镜像被换成了自建镜像，`postgresql.conf` 里 `listen_addresses = 'localhost'`，
容器内只监听回环，所以从 `api` 容器（另一个 network namespace）永远连不上；
`depends_on: condition: service_healthy` 加了也没用（healthcheck 在容器内跑，能通过，骗人）。
